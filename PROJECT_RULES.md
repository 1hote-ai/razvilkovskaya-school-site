# PROJECT_RULES.md

## Правила разработки проекта

### МБОУ «Развилковская средняя общеобразовательная школа с углубленным изучением отдельных предметов»

Данный документ фиксирует обязательные правила, которых должен придерживаться каждый участник разработки. Нарушение этих правил недопустимо без отдельного согласования с архитектором проекта.

---

## 1. Концепция и содержание

- **Не менять утверждённую концепцию** проекта без отдельного задания от архитектора.
- **Не добавлять новые крупные функции** (секции, страницы, интеграции) самостоятельно.
- **Не создавать фальшивые данные о школе**: количество учеников, учителей, кабинетов, достижения, даты, события, историю, характеристики здания.
- **Реальные цифры и факты** добавлять только после их предоставления.
- **Не использовать вымышленные достижения и события.**
- Если для макета временно нужны данные — использовать явно обозначенные placeholders: `[КОЛИЧЕСТВО УЧЕНИКОВ]`, `[ФОТО ШКОЛЫ]` и т.д.

---

## 2. Визуальный язык и контент

- **Сохранять единый визуальный язык** на протяжении всего проекта.
- **Не использовать стоковые фотографии людей** (школьники, учителя).
- **Не использовать фальшивые фотографии.**
- Не использовать типичный шаблон школьного сайта, устаревший корпоративный дизайн, чрезмерный glassmorphism, неон, случайные градиенты, 3D-глобусы, стоковые изображения, чрезмерные анимации.
- Не создавать дизайн, характерный для типичного AI-generated landing page.
- Приоритет: качество композиции, типографики, UX, визуальная целостность.

---

## 3. Адаптивность и доступность

- **Поддерживать responsive design** — проверять desktop и mobile.
- **Учитывать accessibility** (a11y): семантическая разметка, `aria-label`, фокус-состояния, контрасты, навигация с клавиатуры.

---

## 4. Производительность

- **Поддерживать хорошую производительность.**
- **Избегать ненужного JavaScript** — не добавлять логику без реальной необходимости.
- Оптимизировать изображения и ресурсы.
- Следить за размером бандла.

---

## 5. Архитектура и код

- **Не добавлять случайные библиотеки** без согласования.
- **Не создавать огромные монолитные компоненты** — разделять код логично.
- Каждый компонент — в своей папке: `ComponentName/ComponentName.tsx` + `ComponentName.module.scss`.
- Использовать SCSS Modules для стилей.
- Следовать TypeScript strict mode.
- Именование переменных и функций — осмысленное, на английском.
- Комментарии к нетривиальной логике.

---

## 6. Качество и проверки

- **После значимых изменений запускать проверки проекта** (`npm run build`, `npm run lint`).
- **Проверять консоль браузера на ошибки.**
- **Не считать работу завершённой только потому, что приложение запускается** — необходимо визуально проверить результат.
- Проверять корректность работы на desktop и mobile breakpoints.

---

## 7. Git

- Каждый значимый этап — отдельный коммит с осмысленным сообщением.
- Не коммитить `node_modules`, `.env`, сборочные артефакты.
- Придерживаться чистой истории коммитов.
